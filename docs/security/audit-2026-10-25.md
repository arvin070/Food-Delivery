## Findings fixed

| Finding | Impact | Remediation and evidence |
| --- | --- | --- |
| Access JWTs survived logout/password reset/session revocation | High: a captured access token remained usable until expiry | Access tokens now carry a session ID; authentication checks the unrevoked, unexpired session and current account status/role. Regression tests verify logout, password change/reset, and replay revocation. |
| Concurrent refreshes could both rotate the same token | High: refresh reuse was not atomic | User-row locking serializes refresh and password-change paths. Replay revocation commits before an error is returned. Parallel-refresh test verifies one success and no remaining live sessions after replay. |
| Concurrent account OTP verification could consume the same code repeatedly or exceed attempt limits | High: reset/verification replay and guessing race | Issuance and verification serialize on identifier/purpose. Attempts persist even on rejected requests; one verification succeeds under concurrency. |
| Low-entropy account OTP hashes were unkeyed | High under database disclosure: six-digit codes could be enumerated offline | OTPs now use HMAC with a server secret, bound to identifier and purpose; constant-time digest comparison. Existing outstanding account codes must be reissued. |
| Cookie writes relied on CORS/SameSite without explicit CSRF enforcement | Defense-in-depth gap, including same-site sibling origins | Unsafe cookie requests require a configured trusted Origin. Cross-origin and missing-origin writes are rejected; native bearer clients remain supported. Chromium and HTTP checks passed. |
| Proxy headers were implicitly trusted; webhooks bypassed rate limiting | High abuse risk depending on deployment topology | Proxy trust defaults to zero, web proxy strips client forwarding headers, raw webhook route is rate-limited before parsing, refresh is credential-rate-limited. Running-server tests proved spoofed IP headers did not bypass login/webhook limits. |
| Login accepted protocol-relative/backslash return paths | Medium: external post-login redirect | Local-path validation rejects both forms. Both were tested in Chromium. |
| Failed reconciliation attempts updated `lastVerifiedAt` | Incorrect trust metadata for payments/support | Only successful provider application sets verification time; failed polling updates retry scheduling separately. Regression test verifies network failure leaves verification unset. |
| Bcrypt silently truncates new passwords beyond 72 UTF-8 bytes | Ambiguous credential equivalence | Registration/password-reset/change validation enforces the byte limit; Unicode regression test added. Production bcrypt cost below 10 is rejected. |
| Debug database logging included SQL parameters | Sensitive values could enter development logs | Removed SQL parameter logging. SQL structure and duration remain available; credential-bearing request headers remain redacted. Static review, not log-infrastructure testing. |
| Unbounded web-proxy buffering and overly complex validation inputs | Availability risk | Proxy limits streamed request bodies to 1 MiB and applies a 15-second upstream timeout; API bounds JSON size, nesting and collection/node counts before validation. Oversize input tested. |
| Arbitrary image URL schemes and unsupported uploads | Unsafe content handling surface | Profile/meal image URLs restricted to HTTP(S); multipart requests explicitly return 415. No upload/storage subsystem is claimed to exist. |
| Sign-out failures were silently ignored | Misleading UI on a shared device: failed logout appeared to end the session | Sign out now reports failure and permits retry; Chromium tested the actual button and an aborted network request. |
| Missing web security headers | Browser hardening gap | Added nosniff, frame denial, referrer policy and CSP object/base/frame/form restrictions. Chromium response assertions passed. This is not a strict nonce-based script CSP. |
| Critical dependency advisories | Published vulnerable runtime/development dependency versions | Updated compatible versions and overrides; final all-dependency audit reports zero. See advisory references below. |

## End-to-end journey actually executed

`apps/api/tests/parent-delivery-e2e.test.ts` uses the real Express application and PostgreSQL, with independent seeded menu/infrastructure fixtures. Business transitions happen through HTTP endpoints, not by setting order/payment/delivery statuses directly in the database:

1. Parent signs in with cookies.
2. Parent adds Rahul and selects ABC College Gate A and a delivery window.
3. Parent retrieves available slots/menu and adds lunch to the cart. An injected client price is ignored.
4. Checkout creates an AWAITING_PAYMENT order; an identical idempotency key returns the same order.
5. Kitchen cannot prepare the unpaid item.
6. Local mock provider capture is fetched/verified by the payment layer; order becomes CONFIRMED and a receipt is available.
7. Kitchen moves the meal through PREPARING and PACKED.
8. Admin assigns the packed meal, checkpoint and rider to a route.
9. Rider sees the assigned route, picks it up, starts it and arrives at the checkpoint.
10. Parent retrieves the delivery code; rider submits it and backend verifies delivery.
11. Parent retrieves the DELIVERED order and an in-app confirmation naming Rahul and ABC College Gate A.
12. Replayed delivery completion does not create a duplicate notification.

This is an **API end-to-end test**, not a browser walkthrough of every business screen, a real-money payment, a physical delivery, or external SMS/email/WhatsApp/push receipt. The separate Chromium tests cover login, return-path safety, stored XSS, role denial, cookie/CSRF behavior, headers and logout.

## Remaining deployment/integration checks

- Real Razorpay settlement, bank authorization/refunds and real incoming webhooks require configured provider credentials and provider-side testing. Adapter contracts use mocked network responses; the complete flow uses the local mock provider.
- Parent confirmation was verified **in the in-app inbox**. External channels were not sent. In particular, account-reset/verification delivery still uses `UnconfiguredNotifier` in production until a real transport is wired; do not describe production password-recovery email/SMS as operational.
- Rate-limit counters are in process memory. Multiple API replicas require a shared counter store or equivalent gateway enforcement. Trusted proxy hops must match an enforced network topology; the web proxy currently discards client IP forwarding headers, so anonymous limits behind it aggregate at the proxy IP.
- Configure actual web origins in `CORS_ORIGINS`, set `NODE_ENV=production`, keep API ingress private behind the intended proxy, and supply independent strong secrets. Production boot guards and cookie flags were tested with dummy configuration, not a deployed ingress/TLS certificate.
- Production hosting, firewall/WAF, DB least privilege/TLS, backup access, secret rotation, centralized logging, retention and recovery procedures were not accessible/tested. No independent external penetration test, load test, accessibility audit or exhaustive browser/device matrix was performed.
- Admin MFA and a strict nonce-based script CSP are not implemented by this pass. RBAC/session controls and output escaping were tested.

## Release and rerun notes

- No database migration is required for these security changes. Existing schema migrations from prior modules must still be deployed normally.
- Legacy access JWTs without a session identifier are rejected. Users may need to sign in again or refresh; existing account OTPs issued with unkeyed hashes must be reissued.
- Configure allowed browser origins before using cookie-authenticated write requests. Bearer-only native requests without an Origin continue to work.
- Updated tooling requires Node 20.19+ on the 20.x line, or Node 22.12+; this pass ran on Node 26.12.0.
- Run `npm ci`, `npm run db:start`, existing migrations/seed if needed, `npm test`, and `npm run build`. Tests require the local development database and seeded role accounts; do not point them at production.
- Install Chromium with `npx playwright install chromium`; then run `npm run test:browser`. Its config starts and stops dedicated servers on 4107/3107. It uses temporary test users and cleans them up. Traces are disabled to avoid retaining credentials in network traces.
- Run `node scripts/security-runtime-checks.mjs` after building the API. This checks configuration only and sends no external payment or notification requests.
- Run `npm audit` again before deployment; advisory data changes over time.
